# Todo: Git Archaeologist

この文書は、[plan.md](./plan.md)のロードマップを実装可能な単位へ分解したものです。上から順にすべてを実施するのではなく、各フェーズの必須タスクと完了条件を満たした時点で、次のフェーズへ進みます。

## 進め方

- `[ ]`: 未着手
- `[x]`: 完了
- `必須`: フェーズ完了に必要
- `任意`: 評価結果や運用要件に応じて実施
- 各タスクの成果物には、実装だけでなく、設定、スキーマ、テスト、評価結果を含める
- Repository固有の事実は検索基盤に保持し、生成モデルへ知識として埋め込まない
- 観測できた事実、システムによる推論、根拠不足をデータと回答の両方で区別する

## フェーズ1: MVP - 実装理由説明と変更リスク判定

### 目的

単一のGitHub Repositoryを対象に、履歴収集から根拠付きチャット回答までを一巡させます。ファイル・関数単位の実装理由説明と、PRまたは変更内容のリスク判定を、同じRAG基盤で提供できる状態を目指します。

### なぜこのフェーズを最初に行うか

後続の障害分析や行単位追跡も、履歴の収集、対象解決、検索、引用という共通基盤に依存します。最初に一連の処理と評価方法を成立させることで、後続機能を追加したときに、改善したのか悪化したのかを測定できます。

### 1.1 対象と受け入れ条件の固定

- [x] **必須: 対象Repositoryと対象履歴範囲を決める**
  - 目的: 収集量、言語、履歴品質、必要ストレージを見積もれるようにする。
  - 方法: Repository URL、default branch、収集開始時点、PR・Issue・CIの対象範囲、private情報の扱いを設定ファイルに定義する。
  - 成果物: Repository設定、収集対象一覧、除外ルール。
  - 完了条件: 同じ設定から、誰が実行しても同じ範囲を収集できる。

- [x] **必須: MVPで受け付ける入力を固定する**
  - 目的: 対象解決と評価の範囲を広げすぎないようにする。
  - 方法: 「PR URL + ファイル名または関数名」と「コード断片 + 自然言語質問」を正式な入力形式として定義する。
  - 成果物: 入力スキーマ、正常例、曖昧な例、不正な例。
  - 完了条件: 各入力が、対象特定、追加質問、処理不可のいずれかへ決定的に分類される。

- [x] **必須: 暫定的な品質目標を決める**
  - 目的: 主観的な「よさそう」でMVPを完了させないようにする。
  - 方法: 対象解決精度、根拠検索再現率、引用整合率、根拠のない主張率、リスク警告の適合率、回答時間の目標値を定義する。
  - 成果物: 評価指標と受け入れ基準。
  - 完了条件: 評価前に基準が固定され、結果を見て都合よく変更しない運用になっている。

### 1.2 ローカル実行基盤の選定

- [ ] **必須: 実行環境とモデル制約を計測する**
  - 目的: 使用できないモデルや過大なコンテキストを前提に設計しないようにする。
  - 方法: CPU、GPU、VRAM、RAM、ディスク容量を記録し、Embedding、Reranker、生成LLMの候補で速度とメモリを測る。
  - 成果物: ハードウェア情報、候補モデル、量子化方式、実測結果。
  - 完了条件: MVPで使う三つのモデルと最大コンテキスト長が決まっている。

- [ ] **必須: アプリケーションとデータストアの構成を決める**
  - 目的: Raw Archive、イベント、全文検索、ベクトル検索、関係情報の保存先を明確にする。
  - 方法: ローカルで再現可能であり、バックアップとスキーマ更新が可能な構成を比較する。PoCでは運用対象を増やしすぎない。
  - 成果物: 技術選定記録、ディレクトリ構成、起動方法。
  - 完了条件: 空の環境から開発環境とデータストアを再構築できる。

### 1.3 GitHub・Git履歴の収集

- [x] **必須: `gh` CLIの認証と権限を検査する**
  - 目的: 収集途中で権限不足が判明することを防ぐ。
  - 方法: Repository、PR、Issue、Review、Actionsへの読み取り権限を起動時に検査し、不足項目を表示する。
  - 成果物: 接続確認コマンド、権限検査結果。
  - 完了条件: 必要な情報へアクセスできない場合、収集開始前に原因を示して停止する。

- [ ] **必須: GitHub Artifact Collectorを実装する**
  - 目的: PR、Issue、Review、コメント、CI Runを欠落なく取得する。
  - 方法: `gh pr`、`gh issue`、`gh run`と必要な`gh api`呼び出しを組み合わせ、ページング、Rate Limit、再試行、中断再開に対応する。
  - 成果物: ArtifactごとのRaw JSON、取得日時、取得条件、API上のID。
  - 完了条件: 同じ収集処理を再実行しても重複せず、中断地点から再開できる。

- [ ] **必須: Git履歴Collectorを実装する**
  - 目的: GitHub上の議論と実際のコード変更を結び付ける。
  - 方法: Commit metadata、parent、Diff、rename、merge、tag、blameに必要な情報を取得する。対象CommitをSHAで再取得できる形にする。
  - 成果物: Commit metadata、patch、変更ファイル一覧、親子関係。
  - 完了条件: 任意の収集済みCommitについて、変更内容と親Commitを再現できる。

- [ ] **必須: Raw Archiveを不変データとして保存する**
  - 目的: 正規化や要約を変更しても、元の根拠へ戻れるようにする。
  - 方法: Artifact種別と外部IDで保存し、取得時刻、source URL、内容ハッシュ、スキーマバージョンを付与する。秘密情報やCIログのCredentialは保存前に除去する。
  - 成果物: Raw Archive、manifest、改ざん・重複検査。
  - 完了条件: 正規化済みデータの各項目から元データとsource URLへ辿れる。

### 1.4 共通イベントと関係グラフの構築

- [ ] **必須: 共通イベントスキーマを定義する**
  - 目的: Commit、PR、Issue、Review、CI、Revertを同じ探索処理で扱えるようにする。
  - 方法: event ID、種別、時刻、actor、SHA、PR・Issue番号、file、symbol、hunk、本文、source URL、関係、証拠種別を定義する。観測値と抽出・推定値を別フィールドにする。
  - 成果物: バージョン付きイベントスキーマ、正常・異常サンプル。
  - 完了条件: すべてのArtifactを検証可能なイベントへ変換できる。

- [ ] **必須: ArtifactごとのNormalizerを実装する**
  - 目的: GitHub APIやGitの形式差を検索基盤から隠蔽する。
  - 方法: Rawデータを共通イベントへ変換し、変換失敗を握りつぶさず隔離する。再実行時に同じevent IDを生成する。
  - 成果物: Normalizer、変換エラーログ、スキーマ検証テスト。
  - 完了条件: 収集済みデータの変換成功率と失敗理由を集計できる。

- [ ] **必須: Event Graphの関係を生成する**
  - 目的: 一つのCommitから関連PR、Issue、Review、CI、Revertへ探索できるようにする。
  - 方法: 明示リンク、merge SHA、PR番号、Issue参照、Workflowのhead SHAを優先して関連付ける。文字列類似や時刻だけによる関係は推定として保存する。
  - 成果物: イベント間Edge、関係種別、関係の根拠、確信度。
  - 完了条件: Edgeごとに、なぜ関連付けたかを説明できる。

### 1.5 コード・シンボル索引

- [ ] **必須: 対応言語とParserを決める**
  - 目的: 関数やクラスの境界を文字列推測ではなく構文から取得する。
  - 方法: 対象Repositoryの主要言語を集計し、Tree-sitter等のParser対応範囲とfallbackを決める。
  - 成果物: 対応言語一覧、Parser設定、未対応時の動作。
  - 完了条件: MVP評価対象の主要ファイルからシンボルを抽出できる。

- [ ] **必須: Symbol Indexを構築する**
  - 目的: ファイル名、関数名、コード断片をCommit履歴へ接続する。
  - 方法: symbol ID、qualified name、file、範囲、Commit SHA、言語、content hashを保存する。現行版だけでなく、履歴上の主要な版も参照可能にする。
  - 成果物: Code / Symbol Index、索引作成コマンド。
  - 完了条件: ファイル・関数指定から対応シンボルと変更Commitを取得できる。

- [ ] **必須: コード断片の対象解決を実装する**
  - 目的: 利用者がファイル名を知らなくても質問できるようにする。
  - 方法: 完全一致、空白・コメント正規化後の一致、字句類似、シンボル検索の順に候補を作る。複数候補をLLMだけで勝手に一つへ決めない。
  - 成果物: 候補一覧、スコア、曖昧性理由。
  - 完了条件: 一意な候補は自動確定し、複数候補は利用者へ選択肢を提示できる。

### 1.6 RAG検索基盤

- [ ] **必須: 検索単位とchunk方針を定義する**
  - 目的: 長いPRやCIログを機械的な固定長分割で壊さないようにする。
  - 方法: PR本文、Review comment、Issue comment、Diff hunk、Commit messageを意味単位で分割し、親イベントと時刻を保持する。
  - 成果物: chunkスキーマ、分割規則、境界テスト。
  - 完了条件: 各chunkから親イベント、前後文脈、source URLへ戻れる。

- [ ] **必須: キーワード検索とベクトル検索を実装する**
  - 目的: SHA、ファイル名、エラー文字列の完全一致と、自然言語上の意味類似を両立する。
  - 方法: BM25等の全文検索とEmbedding検索を別々に評価し、rank fusionで統合する。検索時にfile、symbol、時刻、Artifact種別で絞り込めるようにする。
  - 成果物: Hybrid Search API、索引作成処理、検索テスト。
  - 完了条件: 正確な識別子と曖昧な質問の両方で関連候補を取得できる。

- [ ] **必須: 多段階検索を実装する**
  - 目的: 単なる類似文書ではなく、対象コードへ因果的に近い履歴を集める。
  - 方法: 対象シンボルの変更Commitを起点にし、Event GraphでPR、Issue、Review、CI、Revertへ展開し、時系列と対象範囲で絞る。
  - 成果物: Query Planner、探索経路ログ、候補イベント一覧。
  - 完了条件: 回答ごとに、どの探索経路で各候補を取得したか確認できる。

- [ ] **必須: Evidence Rerankerを導入する**
  - 目的: 同じファイルを触っただけの履歴より、質問へ直接答えるReviewやIssueを優先する。
  - 方法: 既存Rerankerで質問と候補の関連度を再評価し、明示的な理由、対象シンボル一致、時間的近さ、関係の強さを特徴として扱う。
  - 成果物: Rerank結果、採用・除外理由、モデルバージョン。
  - 完了条件: Rerankなしの検索より、評価データ上の根拠順位が改善する。

- [ ] **必須: Evidence Packを定義する**
  - 目的: 生成LLMへ渡す情報を制御し、引用可能な根拠だけで回答させる。
  - 方法: 質問、対象コード、時系列、原文、Diff、source URL、証拠強度、token数を持つ構造化形式を定義する。コンテキスト上限時の優先順位も決める。
  - 成果物: Evidence Packスキーマ、構築処理、token予算テスト。
  - 完了条件: 生成された各Evidence Packを保存し、回答を再現できる。

### 1.7 チャット入力と質問時処理

- [ ] **必須: Input Interpreterを実装する**
  - 目的: 自然言語入力を検索可能な要求へ変換する。
  - 方法: 実装理由説明、変更リスク判定、対象不明、対応外を分類し、PR URL、file、symbol、code snippet、質問文を抽出する。
  - 成果物: 構造化Query、分類テスト。
  - 完了条件: 代表的な言い換えでも同じ意図と対象情報を抽出できる。

- [ ] **必須: Target Resolverを実装する**
  - 目的: 質問とRepository履歴の対象を決定的に接続する。
  - 方法: URL解析、現行コード検索、Symbol Index、`git log -S`、`git log -G`を順に使い、候補と確信度を返す。
  - 成果物: 解決結果、候補、採用理由、未解決理由。
  - 完了条件: 解決結果を人が確認でき、誤特定の疑いがある場合は回答生成へ進まない。

- [ ] **必須: 未索引の最新PRを質問時に取得する**
  - 目的: 定期同期前のPRでも変更リスクを判定できるようにする。
  - 方法: 入力されたPR URLから最新metadataとDiffだけを取得し、一時的なCurrent Change Contextを作る。過去履歴は既存索引から検索する。
  - 成果物: Current Change Context、取得時刻、head SHA。
  - 完了条件: 判定対象のPRと、比較に使った履歴の時点を回答へ表示できる。

### 1.8 回答生成と引用検証

- [ ] **必須: 回答スキーマを固定する**
  - 目的: 説明内容と根拠不足を機械的に評価できるようにする。
  - 方法: 判定、確認できた理由、根拠、推論、潜在リスク、推奨対応、確信度、不足情報を構造化出力として定義する。
  - 成果物: 回答スキーマ、表示用変換、validation。
  - 完了条件: スキーマ違反時に再生成または安全なエラーへ移行する。

- [ ] **必須: Answer / Judge LLMをRAGのみで動作させる**
  - 目的: SFT前の基準性能と失敗パターンを把握する。
  - 方法: Evidence Pack以外のRepository知識を使わない指示、事実と推論の分離、根拠不足時の棄権をプロンプトへ定義する。
  - 成果物: モデル設定、prompt version、構造化回答。
  - 完了条件: 同じEvidence Packと設定から再評価可能な回答を生成できる。

- [ ] **必須: Citation Verifierを実装する**
  - 目的: 引用が存在するだけでなく、実際に主張を支えていることを確認する。
  - 方法: source IDの存在、引用範囲、時系列の矛盾を決定的に検査し、必要に応じて小型モデルで主張と根拠の含意を判定する。
  - 成果物: 主張単位の検証結果、修正・棄却理由。
  - 完了条件: 存在しない引用、無関係な引用、Evidence Pack外の主要主張を検出できる。

### 1.9 MVP評価と統合

- [ ] **必須: Repository固有の評価セットを作成する**
  - 目的: 検索と回答を、実例に基づいて再現可能に評価する。
  - 方法: 実装理由が明記されたPR、互換性制約、Review指摘、Revert事例から質問を作り、正解対象、必須Evidence、許容される推論、リスクラベルを人手で付与する。
  - 成果物: 評価データ、作成基準、レビュー記録。
  - 完了条件: 簡単な検索例だけでなく、根拠不足、複数候補、誤警告を含む。

- [ ] **必須: 情報漏洩を防ぐ評価分割を行う**
  - 目的: 同じPRの断片が検索・学習・評価へ重複して、見かけの精度が上がることを防ぐ。
  - 方法: PRまたは意思決定単位で分割し、将来SFTする場合に備えて時系列分割も保持する。
  - 成果物: train、validation、testのID一覧と分割理由。
  - 完了条件: 同じ意思決定に属するArtifactが複数splitへ跨っていない。

- [ ] **必須: 検索と回答を別々に評価する**
  - 目的: 原因が検索失敗なのか生成失敗なのかを切り分ける。
  - 方法: 対象解決精度、Evidence recall@k、順位指標、引用整合率、unsupported claim率、棄権精度、リスク警告のprecision・recall、回答時間を測る。
  - 成果物: MVP評価レポート、失敗事例一覧。
  - 完了条件: 各失敗を対象解決、検索、Rerank、生成、引用検証のいずれかへ分類できる。

- [ ] **必須: エンドツーエンドのチャット動作を完成させる**
  - 目的: 個別部品ではなく、利用者の入力から回答までの価値を確認する。
  - 方法: 二つの入力形式、追加質問、回答、根拠表示、処理失敗を一つのチャットフローへ統合する。
  - 成果物: ローカルで起動可能なMVP、実行手順、デモシナリオ。
  - 完了条件: 新しい環境でセットアップし、評価用質問を最後まで実行できる。

### フェーズ1の完了ゲート

- [ ] 対象Repositoryの履歴が再現可能な方法で収集・索引化されている
- [ ] 二つの入力形式から対象コードを解決できる
- [ ] 実装理由説明と変更リスク判定が同じEvidence Pack基盤で動作する
- [ ] 主要な主張から元のCommit、PR、Issue、Review、CIへ辿れる
- [ ] 根拠不足時に断言せず、不足情報を表示できる
- [ ] 評価結果と既知の失敗パターンが記録されている

## フェーズ2: MVPの安定化

### 目的

一度動くMVPを、Repositoryの更新や外部APIの失敗があっても継続利用できる状態へ引き上げます。また、RAGとプロンプトで解決できない問題を計測し、SFTが本当に必要か判断します。

### 2.1 増分同期とデータ保守

- [ ] **必須: 増分同期を実装する**
  - 目的: 毎回全履歴を収集せず、新しいCommit、PR、Issue、Review、CIだけを反映する。
  - 方法: Artifact種別ごとのwatermark、updated timestamp、head SHAを保持し、更新・再オープン・force-pushも検出する。
  - 成果物: 増分Collector、同期状態、再同期コマンド。
  - 完了条件: 同期を繰り返しても欠落・重複せず、更新されたArtifactだけ再処理される。

- [ ] **必須: 索引更新の整合性を保証する**
  - 目的: Raw Archive、イベント、Embedding、Graphの世代がずれることを防ぐ。
  - 方法: 同期単位にversionを付け、失敗時は途中状態を公開しない。削除・編集されたArtifactのtombstone方針を決める。
  - 成果物: 索引version、更新transaction、整合性検査。
  - 完了条件: 回答が参照した索引versionと最終同期時刻を記録できる。

### 2.2 可観測性と障害対応

- [ ] **必須: 質問単位のトレースを実装する**
  - 目的: 誤回答の原因を再現し、修正箇所を特定する。
  - 方法: query ID、対象解決候補、検索query、Graph展開、Rerank順位、Evidence Pack、model version、回答、検証結果を関連付ける。
  - 成果物: 構造化ログ、トレース閲覧方法。
  - 完了条件: 任意の回答について、入力から最終回答まで再現できる。

- [ ] **必須: 外部・モデル障害時の動作を定義する**
  - 目的: GitHub APIやモデルが失敗したときに、古い情報で断言しないようにする。
  - 方法: timeout、Rate Limit、部分取得、モデル停止、context超過、破損索引ごとのfallbackと利用者向けメッセージを定義する。
  - 成果物: エラー分類、再試行方針、障害テスト。
  - 完了条件: 部分的な失敗を正常回答として返さず、利用可能な情報範囲を明示する。

- [ ] **必須: キャッシュを導入する**
  - 目的: 同じ対象への反復質問の待ち時間と計算量を減らす。
  - 方法: 対象解決、検索、Embedding、Evidence Packを索引versionとmodel version付きでキャッシュする。
  - 成果物: キャッシュ層、無効化規則、hit率。
  - 完了条件: Repository更新時に古いキャッシュが誤って再利用されない。

### 2.3 品質改善とSFT判断

- [ ] **必須: 失敗パターンを分類する**
  - 目的: SFTで直らない検索問題へSFTを適用しないようにする。
  - 方法: 誤りを対象解決、収集欠落、関係付け、検索、Rerank、context選択、生成、引用検証へ分類し、発生頻度を集計する。
  - 成果物: Failure taxonomy、優先度付き改善一覧。
  - 完了条件: 上位の失敗原因と改善責任を説明できる。

- [ ] **必須: RAGとプロンプトを先に改善する**
  - 目的: Repository知識をモデルへ埋め込まずに解決できる問題を先に除去する。
  - 方法: chunk、filter、Graph展開、Rerank、Evidence Pack、system promptを一度に一要素ずつ変更して比較する。
  - 成果物: 実験記録、baselineとの差分。
  - 完了条件: 変更ごとの改善・悪化が評価セットで測定されている。

- [ ] **必須: SFTの実施条件を判定する**
  - 目的: Fine-tuningを目的化せず、必要な場合だけ導入する。
  - 方法: 根拠があるのに事実と推論を混同する、根拠外を断言する、回答形式を守らない、因果と時系列を繰り返し誤る問題が残るか確認する。
  - 成果物: SFT実施または見送りのDecision Record。
  - 完了条件: 判断が評価結果と具体的な失敗例で裏付けられている。

- [x] **任意: FT / SFTデータ方針とレコード形式を定義する**
  - 目的: Repository固有事実を暗記させず、Evidence Packの読み方と回答規律だけを学習対象にする。
  - 方法: 学習してよい内容、学習してはいけない内容、SFTレコード、closed-book評価ケース、収集エラー時の人間連絡項目を定義する。
  - 成果物: `src/git_archaeologist/sft_data_policy.py`、`tests/test_sft_data_policy.py`、`data/README.md` のFT / SFTデータ方針。
  - 完了条件: SFTレコードとclosed-book評価ケースをvalidationでき、学習対象外のRepository固有事実や未支持主張を除外できる。

- [ ] **任意: Answer / Judge LLM向けSFTデータを作成する**
  - 目的: Repositoryの事実ではなく、Evidence Packの読み方と回答規律を学習させる。
  - 方法: `質問 + 対象 + Evidence Pack + 理想的な構造化回答`を一例とし、事実、推論、不明、引用、確信度を人手で確認する。
  - 成果物: バージョン付き教師データ、品質レビュー記録。
  - 完了条件: 生のGitHub文書だけを正解として与えず、全回答がEvidence Packで支持されている。

- [ ] **任意: LoRAまたはQLoRAでSFTする**
  - 目的: ローカル環境の制約内で回答規律を改善し、基盤モデルを差し替え可能に保つ。
  - 方法: PR・意思決定単位の分割を維持して学習し、baseline、prompt改善版、SFT版を同じtestで比較する。
  - 成果物: adapter、学習設定、seed、model card、評価結果。
  - 完了条件: 主要指標を改善し、一般的な説明能力と棄権能力を悪化させていない。

- [ ] **任意: 記憶漏洩テストを行う**
  - 目的: SFTがRepository固有の事実をEvidenceなしで回答する状態を検出する。
  - 方法: Evidence Packを空または無関係にした質問を与え、不明と回答するか確認する。学習期間より後の履歴でも評価する。
  - 成果物: closed-book評価、漏洩事例。
  - 完了条件: 根拠がない質問で、学習時に見た事実を断言しない。

- [ ] **任意: Rerankerをランキング学習する**
  - 目的: 生成LLMのSFTとは分離して、根拠順位だけを改善する。
  - 方法: 質問に対するpositive Evidenceとhard negativeを作り、既存Rerankerとの比較評価を行う。
  - 成果物: ランキングデータ、学習済みReranker、検索評価。
  - 完了条件: Evidence recallを維持しながら上位順位の精度が改善する。

### フェーズ2の完了ゲート

- [ ] 増分同期と索引更新が中断・再実行に耐える
- [ ] 回答ごとの検索・モデル処理を追跡できる
- [ ] 主要な失敗パターンに回帰テストがある
- [ ] SFTの実施または見送りが評価結果に基づいて決定されている
- [ ] MVPの品質目標を安定して満たしている

## フェーズ3: 障害・Revert分析

### 目的

CI失敗、不具合報告、修正、Revert、再適用を一つの時系列として再構成し、何が問題で、どの変更で解消され、現在もどの制約が残るかを説明します。

### なぜMVP安定化後に行うか

障害原因はGitHub履歴に明記されないことが多く、時系列上近いだけのイベントを原因と誤認しやすいためです。先に引用、確信度、棄権、評価の仕組みを安定させる必要があります。

### 3.1 CI失敗イベントの構築

- [ ] **必須: CIログの収集範囲と保持方針を決める**
  - 目的: 巨大なログと秘密情報を無制限に保存しないようにする。
  - 方法: failed jobと関連stepを優先し、保持期間、最大サイズ、redaction、再取得可否を定義する。
  - 成果物: CI収集方針、redactionテスト。
  - 完了条件: CredentialやtokenをRaw Archiveと索引へ保存しない。

- [ ] **必須: CI失敗を構造化する**
  - 目的: 生ログ全文ではなく、検索・比較できる障害イベントにする。
  - 方法: Workflow、job、step、test名、error class、message、stack frame、head SHA、発生時刻を抽出し、原文位置を保持する。
  - 成果物: CI failure event、Parser、抽出精度評価。
  - 完了条件: 代表的な失敗から、テスト名、エラー、対象Commitへ辿れる。

- [ ] **必須: 障害signatureを生成する**
  - 目的: 同じ障害の再発を、ログの時刻や一時的な値に影響されず検出する。
  - 方法: path、行番号、ID、時刻を正規化し、test名、error class、主要stack frameを組み合わせてsignatureを作る。
  - 成果物: failure signature、同一・別障害の評価例。
  - 完了条件: 代表的な再発事例をまとめ、異なる障害を過度に統合しない。

### 3.2 Incident GraphとRevert検出

- [ ] **必須: Revertを検出する**
  - 目的: 変更が導入された事実だけでなく、取り消された事実を回答へ反映する。
  - 方法: Commit messageの明示参照、GitHub関係、patch逆適用類似度を組み合わせる。自動推定には確信度を付ける。
  - 成果物: revert edge、reverted / partially reverted / reappliedの状態。
  - 完了条件: 明示的Revertを検出でき、部分Revertを完全Revertと断定しない。

- [ ] **必須: 障害の導入から復旧までを連結する**
  - 目的: 単独イベントではなく、判断過程を時系列で説明する。
  - 方法: introducing change、failed CI、Issue、Review、fix、Revert、reapplyをEvent Graph上で連結する。明示リンクを優先し、時間とfile重複による関係は推定扱いにする。
  - 成果物: Incident Graph、関係根拠、因果確信度。
  - 完了条件: 各因果関係を観測事実または推定として区別できる。

- [ ] **必須: 現在も残る制約を判定する**
  - 目的: 過去に必要だった対策が現在も有効かを説明する。
  - 方法: 修正後の変更、再適用、代替実装、関連テストの存続を追跡し、維持、置換、解消、不明へ分類する。
  - 成果物: constraint status、判定根拠。
  - 完了条件: 「以前問題だった」だけを理由に、現在も危険だと断言しない。

### 3.3 障害回答と変更リスク判定への統合

- [ ] **必須: 障害分析用の回答形式を追加する**
  - 目的: 原因、影響、検出、対応、現在の状態を混同しないようにする。
  - 方法: timeline、observed cause、inferred cause、fix、remaining constraint、related failuresを構造化する。
  - 成果物: Incident Evidence Pack、回答スキーマ。
  - 完了条件: 原因が特定できない場合でも、確認できる時系列だけを提示できる。

- [ ] **必須: 過去の障害を変更リスク判定へ反映する**
  - 目的: 新しい変更が既知の失敗条件を再導入する可能性を警告する。
  - 方法: 変更対象のsymbol、Diff、test、failure signatureをIncident Graphと照合し、具体的な衝突根拠がある場合だけ警告する。
  - 成果物: historical risk evidence、警告理由、抑制規則。
  - 完了条件: 「同じファイルを変更した」だけでは高リスク警告を出さない。

- [ ] **必須: 障害分析の評価セットを作る**
  - 目的: 因果関係のもっともらしい創作を検出する。
  - 方法: 導入、検出、修正、Revertが確認できる事例と、原因不明事例を人手で注釈する。
  - 成果物: Incident評価データ、時系列正解、因果ラベル。
  - 完了条件: 直接原因、推定原因、相関のみを別々に評価できる。

### フェーズ3の完了ゲート

- [ ] CI失敗を検索可能なイベントへ変換できる
- [ ] Revert、部分Revert、再適用を区別できる
- [ ] 障害の導入から復旧までを根拠付きで説明できる
- [ ] 原因不明時に相関を原因として断言しない
- [ ] 変更リスク判定の精度を落とさず、障害履歴を活用できる

## フェーズ4: 行・条件分岐レベルの考古学

### 目的

ファイル・関数単位の説明を、特定行や条件分岐の導入理由と維持理由へ拡張します。rename、move、refactoringを跨いでコードの系譜を追跡します。

### なぜ最後に実装するか

行番号は変更のたびにずれ、`git blame`だけでは移動や書き換えを追跡できません。候補が複数になりやすく、誤った起源へ辿る危険が高いため、先に検索評価と棄権の仕組みを完成させます。

### 4.1 行の起源追跡

- [ ] **必須: 行範囲からBlame履歴を取得する**
  - 目的: 対象行を最後に変更したCommitを起点にする。
  - 方法: porcelain形式のblame、行範囲、親Commitを保存し、mergeや境界Commitの扱いを明示する。
  - 成果物: line origin candidate、Commit、元行範囲。
  - 完了条件: 現行ファイルの指定行から候補Commitへ辿れる。

- [ ] **必須: renameとfile moveを追跡する**
  - 目的: ファイル名が変わっただけで履歴を失わないようにする。
  - 方法: Gitのrename detection、path history、content similarityを使い、旧pathとの関係を保存する。
  - 成果物: file lineage、rename edge、確信度。
  - 完了条件: 評価対象のrename事例で旧ファイルの変更へ到達できる。

- [ ] **必須: 行移動とコード移植の候補を検出する**
  - 目的: blameが新規追加と判定したコードの本当の起源を探す。
  - 方法: 正規化したtoken列、AST subtree、content hash、周辺contextで過去版と比較する。類似候補を一意に断定しない。
  - 成果物: moved / copied candidate、類似度、元位置。
  - 完了条件: 移動、複製、新規実装を評価例で区別できる。

### 4.2 シンボル系譜と条件分岐分析

- [ ] **必須: Symbol Lineageを構築する**
  - 目的: 関数名変更や分割・統合を跨いで設計判断を追跡する。
  - 方法: qualified name、signature、call context、AST similarity、Diff対応からsame、renamed、split、merged、copiedの関係を生成する。
  - 成果物: symbol lineage graph、関係根拠、確信度。
  - 完了条件: 自動追跡できない複雑な分割・統合を不明として扱える。

- [ ] **必須: 条件式の構造変化を追跡する**
  - 目的: 条件分岐の文字列ではなく、判定意図の変化を捉える。
  - 方法: AST上の条件式、branch body、guard clause、関連変数を抽出し、追加、否定、条件追加・削除、順序変更を記録する。
  - 成果物: condition history、semantic diff。
  - 完了条件: 単なる整形変更と意味の変わる条件変更を区別できる。

- [ ] **必須: 関連テストを接続する**
  - 目的: 条件分岐が守っている振る舞いをコードだけで推測しないようにする。
  - 方法: 同一Commitのテスト変更、test名、対象symbol参照、CI failureを条件履歴へ関連付ける。
  - 成果物: condition-to-test edge、テスト変更の時系列。
  - 完了条件: 関連テストがある場合、回答の根拠として提示できる。

### 4.3 導入理由と維持理由の分離

- [ ] **必須: 理由の時点を分けて検索する**
  - 目的: 最初に追加された理由と、その後も残された理由を混同しないようにする。
  - 方法: introduction event、major modification、reviewed preservation、refactor retentionを別々に取得し、時系列化する。
  - 成果物: introduction rationale、maintenance rationale、現在状態。
  - 完了条件: 根拠が片方しかない場合、もう片方を推測で補わない。

- [ ] **必須: 行・条件分岐回答の曖昧性を表示する**
  - 目的: 複数の起源候補から、もっともらしい一つを断定することを防ぐ。
  - 方法: 候補ごとにlineage confidence、supporting events、矛盾を表示し、必要なら利用者へ対象確認を求める。
  - 成果物: 候補付き回答、追加質問フロー。
  - 完了条件: 一意に追跡できないケースを明示的に不明または複数候補として返せる。

- [ ] **必須: 行・条件分岐追跡の評価セットを作る**
  - 目的: blameで解ける簡単な例だけで品質を判断しないようにする。
  - 方法: 単純変更、rename、move、copy、refactor、関数分割、条件書き換え、削除・再導入を含む事例を注釈する。
  - 成果物: lineage評価データ、期待する起源と理由。
  - 完了条件: 起源到達率、誤追跡率、曖昧性検出率を測定できる。

### フェーズ4の完了ゲート

- [ ] 行と条件分岐から起源候補へ辿れる
- [ ] rename、move、copy、refactorを可能な範囲で追跡できる
- [ ] 導入理由と維持理由を分けて説明できる
- [ ] 関連するテスト、障害、Reviewを根拠として提示できる
- [ ] 系譜が曖昧な場合に断言しない

## フェーズ5: 完成形

### 目的

実装理由説明、変更リスク判定、障害分析、行・条件分岐分析を一つのチャット体験へ統合し、Repositoryの更新へ継続的に追従できるローカルシステムとして完成させます。

### 5.1 チャット体験の統合

- [ ] **必須: 質問意図を統合Routingする**
  - 目的: 利用者が機能名を指定しなくても、質問内容から適切な探索を選べるようにする。
  - 方法: 対象粒度、説明要求、リスク要求、障害要求を判定し、必要に応じて複数のQuery Planを組み合わせる。
  - 成果物: 統合Input Interpreter、routingテスト。
  - 完了条件: 同じ会話内でファイル説明から障害分析へ文脈を保って移行できる。

- [ ] **必須: 根拠表示を統一する**
  - 目的: どの機能でも、回答から元履歴へ同じ方法で辿れるようにする。
  - 方法: Commit、PR、Issue、Review、CI、Revertに共通のcitation ID、タイトル、時刻、URL、該当箇所を表示する。
  - 成果物: 共通Evidence表示、時系列表示。
  - 完了条件: 主要な主張を選択すると、対応する原文またはDiffを確認できる。

- [ ] **必須: 会話状態と再質問を実装する**
  - 目的: 同じPRや関数について、対象を指定し直さず掘り下げられるようにする。
  - 方法: 対象、head SHA、Evidence Pack、索引versionを会話状態へ保持し、Repository更新時は再検索を促す。
  - 成果物: session state、文脈更新規則。
  - 完了条件: 古いEvidenceを最新情報として誤利用しない。

### 5.2 ローカル運用と配布

- [ ] **必須: 一括セットアップを実装する**
  - 目的: 開発者以外でも対象Repositoryとモデルを設定して起動できるようにする。
  - 方法: 依存関係、モデル、データストア、認証確認、初回索引を一連の手順へまとめる。
  - 成果物: setupコマンド、設定テンプレート、利用手順。
  - 完了条件: 新しいローカル環境で手順どおりに起動できる。

- [ ] **必須: 定期同期と手動同期を提供する**
  - 目的: Repositoryの新しい履歴を再学習なしで回答へ反映する。
  - 方法: schedulerによる増分同期、質問時の最新PR取得、管理用の手動再同期を実装する。
  - 成果物: 同期job、状態表示、最終同期時刻。
  - 完了条件: 新しいPRやReviewが同期後の検索結果へ反映される。

- [ ] **必須: データ保護と削除手順を整備する**
  - 目的: private Repositoryの履歴、モデル入力、ログをローカルで適切に管理する。
  - 方法: 保存場所、アクセス権、ログredaction、保持期間、Repository切り替え時の削除範囲を定義する。
  - 成果物: データ管理方針、削除・バックアップ手順。
  - 完了条件: 対象Repository由来のデータを列挙し、選択的に削除できる。

### 5.3 性能最適化

- [ ] **必須: エンドツーエンド性能を計測する**
  - 目的: どの処理が利用者の待ち時間と資源消費を支配しているか把握する。
  - 方法: 対象解決、検索、Rerank、LLM生成、引用検証の時間、CPU・GPU・RAM・VRAM使用量を計測する。
  - 成果物: performance profile、改善優先順位。
  - 完了条件: 主要なbottleneckを数値で説明できる。

- [ ] **必須: モデルと索引を最適化する**
  - 目的: 品質を保ちながら、対象ハードウェアで現実的な速度にする。
  - 方法: 量子化、context圧縮、batching、Embedding cache、候補数、Rerank範囲を比較する。
  - 成果物: 推奨runtime profile、品質と速度の比較。
  - 完了条件: 品質基準を下回らず、設定した応答時間目標を満たす。

### 5.4 最終品質保証

- [ ] **必須: 全機能の回帰評価を自動化する**
  - 目的: モデル、検索、prompt、schemaの変更による品質低下を検出する。
  - 方法: 対象解決、検索、説明、リスク、障害、lineage、引用、棄権、性能の評価を一つのsuiteで実行する。
  - 成果物: regression suite、比較レポート、合否判定。
  - 完了条件: version変更ごとに同じ評価を再実行できる。

- [ ] **必須: 人手による受け入れ評価を行う**
  - 目的: 自動指標だけでは測れない説明の有用性と警告疲れを確認する。
  - 方法: 対象Repositoryを知る開発者が、正確性、根拠の十分さ、理解しやすさ、不要警告、調査時間短縮を評価する。
  - 成果物: user evaluation、未解決課題、リリース判定。
  - 完了条件: 重大な誤説明と高頻度の不要警告が許容範囲内である。

- [ ] **必須: 制約と非対応範囲を文書化する**
  - 目的: 履歴に存在しない理由や外部会話まで復元できると誤解されないようにする。
  - 方法: 取得できないArtifact、対応言語、履歴欠損、shallow clone、削除済みデータ、因果推定の限界を記載する。
  - 成果物: 利用上の制約、トラブルシューティング。
  - 完了条件: 回答不能となる代表条件と、その確認方法が利用者に示されている。
